# DBMan

[English](README.md) · **Русский**

Десктопный клиент для разных баз данных в духе DataGrip, на Rust + [egui](https://github.com/emilk/egui) с виджетами [shadcn_egui](https://github.com/georgebigscar-spec/shadcn_egui).

Поддерживаются **PostgreSQL**, **MySQL / MariaDB**, **SQL Server**, **ClickHouse**, **SQLite** и **DuckDB**; новые СУБД подключаются через общий трейт драйвера.

## Что уже умеет

- **Подключения**: создание, редактирование, копирование, удаление, проверка соединения; SSL-режимы `disable / prefer / require / verify-full`; для SQLite и DuckDB выбор файла (у DuckDB можно `:memory:`). Настройки хранятся в `settings.json` в каталоге конфигурации пользователя (пароль сохраняется, только если отмечено «Save password»). Сохранённые пароли хранятся в системном хранилище: Keychain в macOS, Credential Manager в Windows, Secret Service (GNOME Keyring, KWallet) в Linux; у каждого подключения один элемент `DBMan` с паролями базы и SSH. Без хранилища или с `DBMAN_KEYCHAIN=off` пароли остаются в `settings.json` (в Linux и macOS его может читать только владелец). Пароли, уже лежащие в `settings.json`, переезжают в хранилище при следующем сохранении. **SSH-туннели** (вкладка `SSH`): подключение к серверу может идти через SSH-сервер, со входом по паролю или по файлу закрытого ключа (OpenSSH, PEM или PKCS#8, можно с паролем ключа). Хост и порт базы открываются с SSH-сервера, так что `localhost` там означает сам SSH-сервер. Все сессии одного подключения используют один SSH-вход, через него же идут бэкапы, восстановление и экспорт. Ключ хоста проверяется по `~/.ssh/known_hosts` и собственному `known_hosts` DBMan рядом с настройками: ключ нового сервера запоминается при первом подключении, а изменившийся ключ отклоняется. Через туннель DBMan подключается к `127.0.0.1`, а это имя не совпадает с сертификатом сервера, поэтому используйте SSL `require`, а не `verify-full`.
- **Параметры подключения** (вкладка `Options` в диалоге подключения). **Папка**: подключения с одной папкой собраны под ней в дереве, папки идут первыми, а уже используемые папки предлагаются под полем. **Цвет**: метка на строке подключения и его вкладках и линия над содержимым вкладок, чтобы прод был заметен (например, красным). **Только чтение**: выполняются только читающие выражения. Всё остальное (`INSERT`, `UPDATE`, `DELETE`, DDL, `SELECT … INTO`, `WITH`, меняющий данные, `EXPLAIN ANALYZE` изменения, вызовы процедур) отклоняется до отправки на сервер, в консолях и во всех остальных местах DBMan. Где можно, это проверяет и сам сервер: сессии PostgreSQL открываются с `default_transaction_read_only` (поэтому `SELECT` функции, которая пишет, тоже не пройдёт), MySQL с `SET SESSION TRANSACTION READ ONLY`, SQLite с `PRAGMA query_only`, а запросы ClickHouse идут с `readonly=2`. Пункты меню, которые меняют базу (создание, удаление, переименование, очистка, редактор таблиц, импорт, генерация данных, восстановление), скрыты, а просмотр данных не редактирует строки; в дереве у подключения написано `read-only`. **Подтверждать изменения в консолях**: перед запуском, в котором есть выражение, меняющее данные или структуру, консоль показывает первое такое выражение и спрашивает.

- **Database Explorer**: дерево подключение → база → схема (у PostgreSQL) → группы объектов → объекты → колонки, индексы, внешние ключи. Всё грузится лениво при раскрытии.
  - PostgreSQL: таблицы, представления, материализованные представления, внешние таблицы, последовательности, функции и процедуры (с перегрузками), триггеры, типы (enum, domain, composite).
  - MySQL / MariaDB: таблицы, представления, последовательности (MariaDB), функции, процедуры, триггеры.
  - SQL Server: базы → схемы → таблицы, представления, процедуры, функции, триггеры, последовательности, пользовательские типы; комментарии из `MS_Description`.
  - ClickHouse (через HTTP-интерфейс, порт 8123, или 8443 с SSL `require` / `verify-full`): базы → таблицы с движком в подписи, представления, материализованные представления, словари; первичный ключ и data-skipping индексы в структуре. Массивы, map и tuple показываются как JSON, большие целые не теряют точность. Таблицы ClickHouse открываются только для чтения: данные меняются в консоли.
  - SQLite: таблицы, представления, триггеры.
  - DuckDB: подключённые базы (`ATTACH`) → схемы → таблицы, представления, последовательности, макросы, типы; списки, структуры и map показываются так, как их печатает DuckDB.
- **SQL-консоль** с подсветкой синтаксиса. У каждой консоли своя сессия (свои транзакции), как в DataGrip. **Ручная фиксация**: переключатель `Auto-commit` / `Manual commit` на панели консоли. В ручном режиме первый запуск открывает транзакцию (`BEGIN`, в MySQL `START TRANSACTION`, в SQL Server `BEGIN TRANSACTION`), и изменения ждут `Commit` или `Rollback`, которые появляются рядом с меткой `transaction open`. `BEGIN`, `COMMIT` и `ROLLBACK`, написанные в скрипте, тоже учитываются в обоих режимах, как и неявная фиксация MySQL перед DDL. Пока транзакция открыта, режим и базу данных сменить нельзя, а при закрытии консоль спрашивает подтверждение и откатывает транзакцию. `Explain analyze` тоже выполняется внутри транзакции. В ClickHouse транзакций нет, и переключателя там нет. `Ctrl+Enter` выполняет выражение под курсором или выделение, `Ctrl+Shift+Enter` весь скрипт; у каждого выражения свой результат.
  - Автодополнение таблиц, представлений, схем, колонок таблиц и алиасов из запроса, функций и ключевых слов. Открывается, когда набираешь имя или `.`, и по `Ctrl+Space`; `Tab` или `Enter` подставляет выбранное, имена берутся в кавычки, где СУБД это нужно. Таблицы и колонки загружаются с сервера при первом обращении.
- **Параметры в запросах**: `:name`, `${name}` и, в MySQL, SQL Server, SQLite и DuckDB, `?` в выражении спрашиваются перед запуском (в PostgreSQL и ClickHouse `?` это оператор). Строки, комментарии, приведения `::` и `{name:Type}` ClickHouse не трогаются. Диалог показывает выражение с подставленными значениями; они подставляются как написаны, поэтому текст нужен в кавычках (`'Berlin'`), а `NULL` означает пустое значение. Значения запоминаются по имени до следующего раза, и `Explain` тоже их спрашивает.

![Параметры запроса](crates/dbman/tests/snapshots/query_parameters.png)
- **История запросов**: каждое выражение, выполненное в консоли, сохраняется со временем, длительностью и результатом (последние 2000, в `history.jsonl` рядом с настройками). `History` в консоли показывает выражения её подключения, новые сверху, с поиском; клик добавляет выражение в скрипт.
- **Файлы скриптов**: `Script` в консоли открывает `.sql`-файл, сохраняет его (`Ctrl+S`) или сохраняет под другим именем и показывает недавние файлы. На вкладке видно имя файла, а `•` значит, что есть несохранённые изменения.
- **Вкладки возвращаются после перезапуска**: консоли (с текстом, даже несохранённым, базой, файлом и режимом коммита), данные, структура, диаграммы и сессии открываются как были, и впереди снова та вкладка, что была впереди. Ничего не подключается, пока вкладкой не воспользуются. Они хранятся в `workspace.json` рядом с настройками и доступны на чтение только вам; редакторы таблиц, сравнения и копирования не сохраняются, а вкладки удалённого подключения пропускаются.
- **План выполнения**: `Explain` в консоли показывает план выражения под курсором деревом с оценкой строк и стоимости, не выполняя его. `Explain analyze` (PostgreSQL и DuckDB) выполняет выражение и добавляет фактическое число строк и время; полоса показывает долю каждого шага во времени или в стоимости. `Copy plan` копирует ответ СУБД как есть. Каждую СУБД спрашивают по-своему: `EXPLAIN (FORMAT JSON)` в PostgreSQL и DuckDB, `EXPLAIN` в MySQL и MariaDB, `EXPLAIN QUERY PLAN` в SQLite, `EXPLAIN indexes = 1` в ClickHouse, `SET SHOWPLAN_ALL ON` в SQL Server.
- **Форматирование SQL**: `Format SQL` в консоли (`Ctrl+Alt+L`) раскладывает выделенное или весь скрипт по строкам: по предложению на строку, элементы списка `SELECT` и присваивания `SET` по одному на строку, условия `AND` / `OR` на своих строках, подзапросы и CTE с отступом, `CREATE TABLE` по колонке на строку, ключевые слова заглавными (в ClickHouse, где имена чувствительны к регистру, регистр не меняется). Остальные выражения, например тела процедур, триггеры и `GRANT`, остаются как написаны, как и строки и комментарии. Меняются только пробелы и регистр ключевых слов, поэтому смысл скрипта тот же; тест выполняет запросы как написаны и после форматирования на каждой СУБД и сравнивает результаты.

![Форматирование SQL](crates/dbman/tests/snapshots/format_sql.png)
- **Панель значения**: `Value` над таблицей результатов или данными таблицы открывает панель с полным значением выбранной ячейки (в результатах консоли её открывает и двойной клик). JSON-объекты и массивы показываются с отступами, XML по элементу на строку, длинный текст переносится, а байты показываются hex-дампом со смещениями и ASCII. Изображения PNG, JPEG, GIF, BMP и WebP распознаются по первым байтам и рисуются над дампом. На панели видны колонка, её тип, номер строки и размер, а `Copy` копирует значение как есть. Значения больше 1 МБ показываются не целиком.
- **Выделение ячеек**: Ctrl+клик добавляет или убирает ячейку, Shift+клик выделяет прямоугольник между двумя ячейками в том порядке, в котором показаны строки. Если выделено больше одной ячейки, под таблицей видны количество, число NULL, а для чисел сумма, среднее, минимум и максимум. `Copy` или Ctrl+C копирует выделение через табуляцию.
- **Просмотр данных** таблиц и представлений: страницы, фильтр `WHERE`, `ORDER BY`, быстрый фильтр и сортировка в таблице, `NULL` выделен.
- **Редактирование данных** в таблицах: двойной клик по ячейке, `Set NULL` из контекстного меню, `+ Row` и `− Delete` для строк. Изменения подсвечены, пока их не отправили; `Preview SQL` показывает итоговые `INSERT / UPDATE / DELETE`, `Submit` выполняет их в одной транзакции в отдельной сессии. Строки находятся по первичному ключу (без него по всем колонкам), и если `UPDATE` или `DELETE` задел не ровно одну строку, всё откатывается.
- **Экспорт** показанных строк в CSV, TSV, JSON, JSON Lines, SQL `INSERT` или Markdown: в буфер обмена или в файл, а также в файлы Excel и Parquet. В Excel (`.xlsx`) числа, даты, время и логические значения сохраняют типы ячеек, строка заголовков жирная, закреплена и с фильтром, а после 1 048 575 строк начинается новый лист; книга пишется по мере поступления строк. Для Parquet строки собираются во временном файле DuckDB и записываются со сжатием zstd; колонки сохраняют типы (целые, decimal, даты, время, логические, UUID, байты), если в них помещаются все значения, иначе становятся текстом.
- **Экспорт данных целиком** (`Export data…` в меню таблицы или представления, `All rows to a file…` в меню экспорта консоли и просмотра данных) в те же форматы. Идёт фоновой задачей в отдельной сессии: таблица читается страницами по первичному ключу и пишется в файл по мере чтения, так что размер таблицы не упирается в память; в просмотре данных учитываются `WHERE` и `ORDER BY`. Прогресс считается по `COUNT(*)`, `Cancel` останавливает запрос на сервере, а недописанный файл удаляется.
- **Импорт данных** (`Import data…` в меню таблицы) из CSV / TSV (любой разделитель, строка заголовков, поля в кавычках с переводами строк, BOM) , JSON (массив объектов или JSON Lines), Excel (`.xlsx`, `.xlsm`: выбирается лист, даты и время приходят как `YYYY-MM-DD hh:mm:ss`, у формул берётся сохранённое значение, лист читается потоком, а не целиком) и Parquet (через встроенный DuckDB, ничего ставить не нужно). Диалог показывает первые строки файла и сопоставляет колонки по именам (без учёта регистра и `_`) или по порядку; любую колонку можно пропустить. Файл читается в отдельном потоке, строки вставляются пачками многострочных `INSERT` (до 1000 строк для SQL Server). Опции: пустые поля как `NULL`, удалить строки перед загрузкой, всё в одной транзакции с откатом при ошибке (в сообщении номер строк, на которых она случилась). Шестнадцатеричные `0x…` в двоичных колонках становятся байтами, так что экспорт и импорт двоичных данных сходятся. Для SQL Server включается `IDENTITY_INSERT`, если загружаются значения identity-колонки, а в PostgreSQL после загрузки последовательности сдвигаются за максимальное значение.
- **Новая таблица из файла** (`New table from a file…` в меню схемы, а у СУБД без схем в меню базы). Типы колонок подбираются по первым 10 000 строкам: целые, decimal с нужной точностью, дробные, логические, даты, время, UUID, байты `0x…`, остальное текст; коды с ведущими нулями вроде `007` остаются текстом. Имена и типы можно поправить перед импортом. Таблица создаётся перед загрузкой и удаляется, если импорт не удался.
- **ER-диаграмма** схемы (`ER diagram` в меню схемы, а у СУБД без схем в меню базы): таблицы с колонками, первичные (оранжевая точка) и внешние (синяя) ключи, связи от колонки внешнего ключа к колонке, на которую он ссылается. «Воронья лапка» у дочерней таблицы, если на одну строку родителя приходится много строк, пунктир у необязательной связи (ключ допускает `NULL`). Таблицы из других схем, на которые есть ссылки, рисуются пунктирной рамкой. Раскладка автоматическая: родительские таблицы левее дочерних, порядок подобран так, чтобы линии меньше пересекались, несвязанные таблицы сеткой ниже. Таблицы перетаскиваются мышью, холст двигается перетаскиванием фона и колесом, масштаб меняется с `Ctrl` + колесо; `Fit` показывает всё, `Keys only` оставляет только ключевые колонки, поиск находит таблицу и подсвечивает её связи, двойной клик открывает данные. Экспорт в SVG, Mermaid (`erDiagram`) и Graphviz DOT, в файл или в буфер обмена. Структура читается в отдельной сессии, с прогрессом.
- **Сравнение схем и данных** (`Compare with…` в меню схемы, а у СУБД без схем в меню базы): источник сравнивается со схемой на любом подключении, той же СУБД или другом сервере.
  - Вкладка `Structure`: таблицы по колонкам (тип, `NULL`, значение по умолчанию, автоинкремент, комментарий), первичному ключу, индексам и внешним ключам; представления, процедуры, функции, триггеры, последовательности и типы по определению. Для каждого объекта видно, что изменилось, его определение в источнике и в цели и выражения для синхронизации. Скрипт создаёт новые объекты (таблицы в порядке внешних ключей), меняет изменённые через `ALTER TABLE` (в SQLite таблица пересоздаётся с копированием строк) и по желанию удаляет лишние; удаление по умолчанию не отмечено. Имена схемы в определениях заменяются на целевые.
  - Вкладка `Data`: строки каждой таблицы сопоставляются по первичному ключу, на любых двух СУБД. Цель читается постранично и хранится в памяти как хеши колонок, источник проходит мимо неё потоком. Скрипт из `DELETE` (пачками по ключу), `UPDATE` только изменённых колонок и многострочных `INSERT` (с `IDENTITY_INSERT` в SQL Server и сдвигом последовательностей в PostgreSQL); удаления идут от дочерних таблиц к родительским, вставки наоборот. В ClickHouse это мутации `ALTER TABLE … UPDATE / DELETE`, которые ждут завершения.
  - Скрипт можно посмотреть, скопировать, сохранить в `.sql`, открыть в консоли цели или применить фоновой задачей: в одной транзакции там, где DDL транзакционный (PostgreSQL, SQL Server, DuckDB, а для данных все, кроме ClickHouse), с откатом при ошибке. Сравнение идёт в отдельных сессиях с прогрессом и кнопкой `Stop`.
- **Копирование таблиц между подключениями** (`Copy to another connection…` в меню схемы или базы, `Copy to…` в меню таблицы): отмеченные таблицы со строками переносятся в схему на любом подключении, в том числе между разными СУБД (все 36 пар из шести). Недостающие таблицы создаются в порядке внешних ключей, типы переводятся на язык цели (например, `tinyint(1)` MySQL становится `boolean` в PostgreSQL, `bytea` становится `varbinary(max)` в SQL Server, ключ в ClickHouse становится `ORDER BY`), а вкладка заранее показывает колонки с типами в источнике и в цели. Для таблиц, которые в цели уже есть, можно добавить строки, заменить их или пересоздать таблицу; перед заменой и пересозданием спрашивается подтверждение. Строки читаются страницами по первичному ключу и вставляются пачками, по транзакции на таблицу (кроме ClickHouse), с `IDENTITY_INSERT` в SQL Server и сдвигом последовательностей в PostgreSQL. Копирование идёт фоновой задачей с прогрессом и `Cancel`.
- **Генератор тестовых данных** (`Generate test data…` в меню таблицы): для каждой колонки генератор подбирается по имени и типу: последовательности для ключей, имена, email, телефоны, города, компании, слова, числа и даты в диапазоне, UUID, JSON и байты; значения enum в MySQL и ClickHouse берутся из типа, а внешние ключи получают значения из родительской таблицы. Любой генератор и его настройки можно поменять, в колонки, допускающие `NULL`, `NULL` попадает с заданной долей. Значения первичных ключей и уникальных колонок не повторяются, в том числе при добавлении строк позже, а последовательности продолжаются после максимального значения в таблице. Предпросмотр показывает первые строки, одно и то же зерно даёт одни и те же строки. Строки вставляются пачками в одной транзакции (кроме ClickHouse) фоновой задачей, по желанию после удаления имеющихся.
- **Структура и DDL** любого объекта: колонки, индексы, внешние ключи и `CREATE`-выражение.
- **Редактор таблиц** (`New → Table`, `Modify Table…`): колонки с типом, `NOT NULL`, значением по умолчанию, автоинкрементом и комментарием, первичный ключ, индексы и внешние ключи. Внизу живой SQL-предпросмотр; изменения выполняются в одной транзакции. Для PostgreSQL генерируется `ALTER TABLE` с `RENAME COLUMN`, `TYPE … USING`, identity; для MySQL `CHANGE COLUMN` с пересозданием затронутых внешних ключей; для SQL Server `ALTER COLUMN`, `sp_rename`, `IDENTITY`, пересоздание default-ограничений и комментарии через extended properties; для ClickHouse `MergeTree` с `ORDER BY` по первичному ключу, `MODIFY COLUMN`, `RENAME COLUMN`, data-skipping индексы и комментарии; для SQLite таблица пересобирается через временную копию, если `ALTER` не хватает; для DuckDB `ALTER` как в PostgreSQL, а чего DuckDB не умеет (автоинкремент, смена ключей у существующей таблицы, действия внешних ключей), редактор пишет в заметках к скрипту.
- **Создание и удаление** баз и схем, удаление, переименование и очистка (`TRUNCATE`) объектов из контекстного меню, с показом точного SQL перед выполнением (`CASCADE` и `WITH (FORCE)` для PostgreSQL). Шаблоны `CREATE` для представлений, функций, процедур, триггеров, последовательностей открываются в новой консоли.
- **Окно никогда не ждёт базу**: подключения, запросы, загрузка метаданных, диалоги файлов, экспорт и импорт идут в фоне. У консоли и просмотра данных есть таймер и кнопка `Stop`, которая отменяет запрос на сервере (`pg_cancel` в PostgreSQL, `KILL QUERY` в MySQL, в SQL Server сессия переоткрывается, и открытая транзакция откатывается, `KILL QUERY` по `query_id` в ClickHouse, `sqlite3_interrupt` в SQLite, `interrupt` в DuckDB). Просмотр данных работает в своей сессии, поэтому медленная страница не задерживает дерево объектов.
- **Сеансы** (`Sessions` в меню серверного подключения): кто подключён и что выполняет, по `pg_stat_activity` в PostgreSQL, `information_schema.PROCESSLIST` в MySQL и MariaDB, `sys.dm_exec_sessions` и `sys.dm_exec_requests` в SQL Server и `system.processes` (выполняющиеся запросы) в ClickHouse. В каждой строке пользователь, база, клиент, приложение, состояние, сколько сеанс в нём находится, чего он ждёт и его текущее или последнее выражение; сеанс, через который DBMan получает список, помечен `this`. Список обновляется каждые 3 секунды (`Auto-refresh` это выключает), `Hide idle` оставляет только сеансы, которые что-то выполняют, а фильтр ищет по всем колонкам. Клик по строке показывает выражение целиком под таблицей. Там и в меню строки `Cancel query` останавливает выражение, не закрывая сеанс (`pg_cancel_backend`, `KILL QUERY`, в ClickHouse `KILL QUERY WHERE query_id`), а `Kill session…` после подтверждения отключает сеанс, и его открытая транзакция откатывается (`pg_terminate_backend`, `KILL CONNECTION`, `KILL` в SQL Server). `Open query in a console` и `Copy query` забирают выражение.

![Сеансы](crates/dbman/tests/snapshots/sessions.png)
- **Пользователи и роли** (`Users and roles` в меню серверного подключения; пункт есть, только если подключённый пользователь может управлять пользователями: суперпользователь или роль с `CREATEROLE` в PostgreSQL, учётная запись с `CREATE USER` в MySQL, `sysadmin` или обладатель `ALTER ANY LOGIN` и `ALTER ANY USER` в SQL Server, пользователь ClickHouse с правом управления доступом; у SQLite и DuckDB пользователей нет). Слева пользователи и роли: в PostgreSQL пользователи это роли с правом входа, в MySQL и MariaDB учётные записи `user@host`, в SQL Server пользователи и роли одной базы, в ClickHouse его пользователи и роли; `Show built-in` добавляет роли `pg_*`, `mysql.sys`, `dbo`, фиксированные роли базы и т. п. Справа выбранный: атрибуты (суперпользователь, создание баз и ролей, наследование, репликация, обход защиты строк, блокировка учётной записи MySQL, отключённый логин SQL Server), роли, в которые он входит, участники роли (`×` убирает участника) и права, выданные ему напрямую: объект, право и может ли он передавать его дальше. В PostgreSQL и SQL Server права показываются для базы, выбранной на панели. `New user…`, `New role…` и `Edit…` задают имя (и хост в MySQL), пароль и атрибуты; `Add to role…` и `Add member…` выдают роль, с правом администрирования, где оно есть; `Grant privileges…` выдаёт права на таблицу, представление, схему, базу, последовательность, функцию, все таблицы схемы или весь сервер, смотря по СУБД, с правом передачи; `Revoke…` в меню права отзывает его, `Drop…` удаляет пользователя или роль. Каждый редактор показывает точный SQL (`CREATE ROLE`, `CREATE USER`, `ALTER ROLE`, `GRANT`, `REVOKE`, `ALTER ROLE … ADD MEMBER`…) до выполнения. Новый пользователь SQL Server получает логин с тем же именем; при удалении пользователя логин остаётся. В подключении только для чтения вкладка только показывает.

![Пользователи и роли](crates/dbman/tests/snapshots/users_and_roles.png)
- **Резервное копирование и восстановление** из контекстного меню базы, схемы или таблицы (`Back up…`, `Restore…`). Задача идёт в фоне: панель «Background tasks» показывает прогресс, размер файла, время, журнал инструмента и кнопку `Cancel`; окно остаётся рабочим.
  - PostgreSQL: `pg_dump` в форматах custom, plain SQL, directory (параллельно) и tar; выбор схем и таблиц, пропуск данных отдельных таблиц, `--no-owner`, `--no-privileges`, для SQL `DROP`/`CREATE DATABASE`/`INSERT`. Восстановление через `pg_restore` (формат определяется по файлу; очистка, создание базы, одна транзакция, параллельность) или `psql` для SQL-скриптов.
  - MySQL / MariaDB: `mysqldump` или `mariadb-dump` (под MariaDB берётся свой), `--single-transaction`, процедуры, триггеры, события, `DROP TABLE`, `CREATE DATABASE`, hex для двоичных данных. Восстановление клиентом `mysql` / `mariadb` с прогрессом по прочитанной части файла.
  - SQLite: копия через online backup API (база остаётся доступной) или `VACUUM INTO`, проверка `quick_check`; восстановление копирует страницы обратно в открытую базу.
  - SQL Server: `BACKUP DATABASE` / `BACKUP LOG` (полная, разностная, журнал; copy-only, сжатие, контрольные суммы, проверка `RESTORE VERIFYONLY`) и `RESTORE DATABASE` с заменой, отключением других сессий, `NORECOVERY` и переносом файлов в папки сервера по умолчанию, чтобы восстановить копию под новым именем. Файл лежит на сервере, процент выполнения берётся из `sys.dm_exec_requests`, `Cancel` завершает задачу через `KILL`.
  - ClickHouse: `BACKUP` / `RESTORE` базы или таблицы на диск сервера (`Disk('backups', …)`), в файл (`File(…)`) или в S3, инкрементальные копии поверх предыдущей (`base_backup`), только структура, восстановление под другим именем или с добавлением строк в существующие таблицы. Задача идёт асинхронно (`ASYNC`), прогресс и ошибки берутся из `system.backups`, `Cancel` убивает её запрос. Ключ S3 в журнале и предпросмотре скрыт. Диск и путь должны быть разрешены в настройках сервера (пример в `ci/clickhouse-backups.xml`).
  - DuckDB: `EXPORT DATABASE` в папку (Parquet со сжатием zstd или CSV) либо копия в новый файл `.duckdb` (`ATTACH` + `COPY FROM DATABASE`); восстановление `IMPORT DATABASE` из папки или копированием из файла. Внешние инструменты не нужны, а база во время копии остаётся открытой: файл DuckDB можно открыть в процессе только один раз, поэтому все сессии на один файл делят один экземпляр базы.
  - Инструменты ищутся в `PATH` и в обычных местах установки (Homebrew, Postgres.app, Program Files, `/usr/lib/postgresql/*/bin`); папку можно указать в диалоге. Пароль передаётся через переменные окружения, в командной строке и журнале его нет.
- Интерфейс на английском (по умолчанию) и русском: язык переключается в правом верхнем углу и запоминается. Переводы лежат в `crates/dbman/locales/ru.json`, тест проверяет, что у каждого текста интерфейса есть перевод.
- Светлая и тёмная темы.

Горячие клавиши: `Ctrl+T` новая консоль, `Ctrl+W` закрыть вкладку, `Ctrl+Space` автодополнение в консоли, `Ctrl+S` сохранить скрипт консоли, `F4` открыть выбранный объект, двойной клик по таблице открывает данные.

## Запуск из исходников

```sh
cargo run --release
```

Первая сборка дольше обычной: DuckDB компилируется из исходников C++ (около 10 минут на 4 ядрах), дальше он берётся из кэша.

На Linux для диалога выбора файла нужен xdg-desktop-portal (есть в обычных GNOME/KDE).

## Архитектура

```
crates/
  dbman-core/     модели и трейт Connection, без GUI и драйверов
  dbman-drivers/  реализации: postgres (tokio-postgres), mysql (mysql_async), sqlite (rusqlite), duckdb (duckdb-rs, собирается из исходников), mssql (tiberius), clickhouse (HTTP через reqwest)
  dbman/          приложение на eframe + shadcn_egui
```

- **`dbman-core`**: `ConnectionConfig` и `DbKind`; трейт `Connection` (список баз, схем, объектов, структура таблицы, DDL, выполнение SQL); модели результата (`QueryResult`, `Cell`) и схемы (`DbObject`, `TableDetails`); токенизатор SQL для подсветки и разбиения скрипта на выражения с учётом диалекта (`$$`-строки PostgreSQL, обратные кавычки и `#`-комментарии MySQL), экранирование идентификаторов и строк.
- **`dbman-drivers`**: по модулю на СУБД и функция `connect(&ConnectionConfig)`; `backup.rs` запускает резервное копирование, `transfer.rs` экспорт и импорт данных (форматы файлов и сборка `INSERT` в `dbman-core::export`, `dbman-core::import` и `dbman-core::xlsx`; `files.rs` читает и пишет Parquet через DuckDB). Чтобы добавить СУБД, нужен вариант в `DbKind`, реализация `Connection` и строка в `connect`.
- **`dbman`**: интерфейс никогда не ждёт базу. Запросы выполняются на tokio-рантайме, результаты приходят событиями через канал и забираются каждый кадр (`events.rs`). Дерево (`explorer.rs`), вкладки (`tabs.rs`), сетка результатов (`grid.rs`), редактор данных (`data_view.rs`), редактор таблиц (`table_editor.rs`, DDL строит `dbman-core::ddl`), диалоги подтверждения (`prompt.rs`), выполнение изменений в отдельной сессии (`exec.rs`), редактор SQL (`sql_editor.rs`), диалог подключения (`connection_dialog.rs`), ER-диаграмма (`er_view.rs`, модель, раскладка и экспорт в `dbman-core::er`), сравнение схем и данных (`compare_view.rs`, сравнение и скрипты в `dbman-core::compare`, чтение и запуск в `dbman-drivers::compare`), копирование между подключениями (`copy_view.rs`, перевод типов и значений в `dbman-core::copy`, сам перенос в `dbman-drivers::copy`), генератор тестовых данных (`generate_dialog.rs`, генераторы в `dbman-core::generate`, вставка в `dbman-drivers::generate`), выбор цели для сравнения и копирования (`target_picker.rs`), язык интерфейса (`i18n.rs`), диалоги резервного копирования (`backup_dialog.rs`) и переноса данных (`transfer_dialog.rs`), фоновые задачи (`jobs.rs`), сеансы сервера (`sessions_view.rs`, запросы для каждой СУБД в `dbman-core::sessions`), пользователи и роли (`admin_view.rs`, запросы для каждой СУБД в `dbman-core::admin`).

## Тесты

```sh
cargo test --workspace
```

Тесты драйверов для SQLite и DuckDB идут всегда; для PostgreSQL, MySQL, SQL Server и ClickHouse нужны адреса серверов:

```sh
DBMAN_TEST_POSTGRES=postgres://postgres:secret@127.0.0.1:5432/postgres \
DBMAN_TEST_MYSQL=mysql://root:secret@127.0.0.1:3306/dbman_test \
DBMAN_TEST_MSSQL=mssql://sa:Secret_1@127.0.0.1:1433/dbman_test \
DBMAN_TEST_CLICKHOUSE=clickhouse://default:secret@127.0.0.1:8123/dbman_test \
cargo test --workspace
```

`crates/dbman/tests/ui.rs` прогоняет окно целиком на примерной базе SQLite. С `DBMAN_SCREENSHOTS=1 UPDATE_SNAPSHOTS=1` он перерисовывает скриншоты в `crates/dbman/tests/snapshots/` (нужен wgpu-адаптер; без GPU подойдёт `mesa-vulkan-drivers`).
